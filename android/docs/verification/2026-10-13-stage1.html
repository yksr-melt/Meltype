点分かっていること
変換結果が返るたびに、候補バーを作り直している。候補の数は中央値で 35 個、多いときは 209 個あり、その数だけ表示の部品を作り直す。エミュレーター A では 1 回あたり中央値 5 ミリ秒（release）／11 ミリ秒（デバッグ）、候補が 100 個以上のときは 19 ミリ秒／38 ミリ秒かかった。画面のスレッドで行うので、そのあいだキーの反応と描画が待たされる。仕様の目安（16 ミリ秒）は「変換を待たない分」が対象なので外れてはいないが、打ち心地に効く。実機で測ってから、候補の数を絞るか、見える分だけ作るかを決めるのがよい。
画面の大きさを adb shell wm size で変えると、キーボードのいちばん下の段がナビゲーション領域の下に隠れる。エミュレーター A で wm size 1080x1680 → キーボードを出す → 下の段が欠ける。大きさを戻しても、キーボードのプロセスを起動し直すまで直らない。ナビゲーション領域の高さが、キーボードに知らされなくなっている。原因は分かっていない。表示の細かさ（wm density、設定の「表示サイズ」にあたる）を変えたときは起きない。回転、ライト/ダーク、プロセスの起動し直しでも起きない。実物の小さい画面（エミュレーター B）でも起きない。ふつうの使い方で起きるかは不明（画面の解像度を切り替えられる端末や、折りたたみ端末では試せていない）。

確かめていないことと、その理由

確かめていないこと理由
実機（arm64）でのすべて。arm64 の libmozc.so が動くこと、指で打ったときの感覚、振動、フリックの判定の具合、実機での見た目。実機に入れるのは、この確認のあとで利用者と一緒に行うと決めてある。arm64 の libmozc.so は、まだどの端末でも読み込まれたことがない。
スマートフォンでの性能（仕様 11 の「性能」の 3 項目）。同じ。上の値はエミュレーターのもの。計測用のログは実機でもそのまま使える。
Android 9〜14（API 28〜34）。確かめたのは Android 8.0 と 15 だけ。ナビゲーション領域の扱いは Android 11 を境に処理が分かれていて、古い側は 8.0、新しい側は 15 でだけ見た。
危ない点として: Android 9〜14 での、導入画面の下の余白。導入画面は、システムのバーとキーボードの分を自分で空けている（SystemBars.kt。Android 10 以前は画面を縮める指定 adjustResize に任せ、Android 11 以降はキーボードの高さだけ下を自分で空ける）。動かしたのは API 26 と API 35 だけ。あいだの版（API 28〜34）では、下の余白が二重に取られる（試し書き欄の下に大きなすき間ができる）か、取られない（欄がキーボードやナビゲーション領域の下に隠れる）おそれがある。とくに境目の API 29・30 と、ジェスチャーナビゲーションが入った API 29 以降の古い側。キーボード本体の下の余白（KeyboardService）も、同じ 2 つの版でしか見ていない。あいだの版のエミュレーターは用意していない。
入れた直後、辞書を写している最中に打ったときの動き。最初の版は「打った文字はすべて入り、欄を選び直さなくても変換結果が出た」と書いたが、残っている根拠は 53-first-use.png の 1 枚で、写している最中だったかどうかは分からない。やり直すにはアプリを入れ直す必要があり、今回はしていない。Mozc を開けなかったあとのやり直し（修正で足した）は、別に確かめた（下の節）。
削除の押し続けのうち、未確定文字から確定済みの文字へそのまま続くこと、空の欄での押し続け、← → の押し続け。最初の版は確かめたと書いたが、記録が残っていない。やり直したのは、確定済みの文字を消す回数だけ。
アプリを切り替えたとき、移った先のアプリの欄に未確定文字が入らないこと。最初の版は「ほかの欄には入らない」と書いたが、記録が残っていない。やり直しでは、元の欄に 1 回だけ残ることを見た。移った先では欄を選んでいない。
目安を超えた性能の値の原因。調べていない（目安を超えたもの）。修正のあとのビルドでの計測もしていない。
Android 8.0 でのパスワード欄・数字欄、長い時間の使用、導入画面の全体とほかのアプリの中でのダーク。エミュレーター B では、起動・有効化・変換・配列・回転までを見て終えた。修正のあとに足したのは、release ビルドでの変換、横画面の高さ、キーボードのダークだけ。
0.1 秒より短い間隔での連打、2 本の指での同時押し。adb で送れる操作の限界。同時に送ると、Android が不正な操作として捨てる。古い変換結果を捨てる処理は、0.1 秒間隔（変換は 0.04 秒ほど）では十分に試せていない。単体テストでは確かめてある。
キーを押したときの振動。エミュレーターでは分からない。
確定キーの「送信」の表示。その指定をする欄が、エミュレーターのアプリに見つからなかった。単体テストでは確かめてある。
メモアプリでの入力。エミュレーターに入っていない。
Mozc のビルドスクリプトの、キャッシュのない状態からの実行と、失敗したときの動き。30〜40 分かかるため。今回はキャッシュのある状態で通した。
配るための署名での release ビルド。鍵をまだ用意していない。今回はデバッグ用の鍵で署名した。
画面の解像度を切り替えられる端末、折りたたみ端末、タブレット。手元にない。上の「画面の大きさを変えると下の段が隠れる」が実際に起きるかは、こうした端末で見る必要がある。
ログの確認のうち、最初の約 10 分。ログを取り続ける仕組みを動かしたのが途中からだった。同じ種類の操作は、そのあとにもう一度行っている。

修正のあとにエミュレーターで確かめたこと

エミュレーター A（Android 15）。とくに書いていなければ、デバッグビルド（7ea0e3e）。入力先は、Chrome で開いたテスト用のページの欄、Chrome のアドレスバー、メッセージ、設定の Wi‑Fi パスワード欄、導入画面の試し書き欄。

項目やったこと結果
空白は予測候補を選ばない「きょうはてんきがいい」を打った。候補バーには、変換結果の次に、前に覚えさせた長い文（予測候補）が 2 つ並んでいる。空白を押した。別に「あしたはあめ」で空白を 9 回押した。空白は予測候補を飛ばし、その先の、先頭の文節の候補を選んだ（09-web-url-space.png、31-space-skips-prediction.png）。9 回のあいだ、選ばれた表示はどれも打った読みと同じ長さで、長い文は一度も選ばれなかった。予測候補のタップでの確定は、単体テストでだけ確かめた。
URL の欄（Chrome のアドレスバー）アドレスバーをタップ → あ/A → 「きょうはてんきがいい」 → 空白 → 確定 → もう一度確定。英字配列で始まる（13-omnibox-qwerty.png）。かなにするとライブ変換と候補が出る（14-omnibox-live.png）。確定キーの表示は「開く」。1 回目の確定で未確定文字が確定され、2 回目で検索が実行された。
URL の欄では学習しないページの中の url の欄で、「かいとう」の 3 番目の候補を空白で選んで確定し、もう一度「かいとう」を打った。同じことを text の欄でもした。url の欄では、2 回目も元の第一候補が出た（学習されていない）。text の欄では、2 回目は選んだ候補が第一候補になった。
パスワードの欄（ウェブのページ）password の欄で「ab」 → あ/A → 「か」 → 3 秒待つ → ゛゜小 → もう一度 → 「は」に ゛゜小 を 2 回 → 「ん」に ゛゜小 → 「あ」を 3 回 → 削除。下線付きの文字は出ない。打った文字は 3 秒後には伏せ字になっている（05-password-ka-after-3s.png）。打った直後の 0.3 秒の時点では、その 1 文字が下線なしで読める（03-password-ka-masked.png）。これは Android と Chrome が、どのキーボードのどの文字でも行う「打った直後の 1 文字を短く見せる」表示で、直す前の「次のキーを押すまでずっと読める」とは違う。゛゜小 で か → が → か、は → ば → ぱ。「ん」は変わらない。「あ」3 回は「あああ」。削除で 1 文字消える。
パスワードの欄（Android の欄。設定の Wi‑Fi パスワード）同じ操作。最後に「パスワードを表示」にチェックを入れて中身を読んだ。同じ結果。3 秒後には伏せ字（62-wifi-password-ka-after-3s.png）。中身は「abがぱあ」で、打ったとおり（64-wifi-password-shown.png）。
パスワード以外の「変換しない」欄email の欄で「a」 → あ/A → 「か」 → ゛゜小 → 「な」 → 削除 → 削除。number の欄で数字を打ち、「戻る」を押した。今までどおり、最後の 1 文字だけを下線付きで持つ（33-email-held.png）。゛゜小 と削除は、その 1 文字に効く。数字の欄は数字・記号で始まり、「戻る」で英字になる。
横画面の高さ未確定文字がある状態で横向きにして、キーボードの占める範囲を dumpsys window で読み、スクリーンショットを撮った。横向きのまま、タップ、上フリック、押したままの案内（上の段と下の段）、空白、確定、英字配列を試した。縦に戻した。横向き（高さ 1080 ピクセル = 411dp）で、キーボードの範囲は上から 503 ピクセルの位置から下まで。内訳は、候補バー 36dp + キー 4 段 × 40dp = 196dp（514 ピクセル）と、ナビゲーション領域 24dp（63 ピクセル）。直す前は 745 ピクセル（アプリに残るのは 335）。縦では 54dp と 44dp のまま。向きを変えても、キーボードのプロセスは同じまま。案内は欠けない（22-landscape-guide-top-row.png、23-landscape-guide-bottom-row-down.png）。キーの文字は読める（21-landscape-composing.png、25-landscape-qwerty.png）。アプリに残る高さは 503 ピクセルで、画面の 46.6%。半分には届いていない。キーと候補バーだけなら 47.6% だが、その下のナビゲーション領域のぶんで半分を超える。
横画面の高さ（Android 8.0、エミュレーター B、release ビルド）導入画面の試し書き欄で、横向きにして欄をタップし、上フリックとタップで打った。横向き（高さ 1080 ピクセル = 360dp）で、キーボードは下の 588 ピクセル（196dp。この版の横向きではナビゲーションバーは右に出る）。アプリに残るのは 492 ピクセルで、45.6%。ここでも半分に届かない。打った文字は正しく入った（96-api26-landscape-keyboard.png）。導入画面を回すとキーボードが閉じるのは、前から分かっている点のまま。
回転（Chrome、候補を選んだ状態）Chrome のページの text の欄で、候補を選んだ状態で横向きにして戻す、を繰り返した。直す前のビルド、別のキーボード（Gboard）でも同じことをした。文字は、どの回も 1 回だけ残った。キーボードは、横向きにしたときに閉じることがある: 修正のあとのビルドで 10 回中 3 回（別の 8 回では 3 回）。直す前のビルドでは 10 回中 0 回。Gboard では 10 回中 10 回閉じた（fixwave-rotation-chrome.log）。高さを 54dp・44dp に戻したビルドでは 9 回中 0 回だったので、横画面の高さを変えたことで起きるようになった動きである。Gboard では必ず閉じることから、Chrome の側の動作（回したときに、ページの入力まわりの表示を閉じる）とみているが、Chrome の中は調べていない。閉じたあとは、欄をタップすれば出る。メッセージでは 6 回中 0 回。
Mozc を開けなかったときのやり直し辞書を置くフォルダーを、わざと同じ名前のファイルに置き換えてから、キーボードのプロセスを終了させた（開くのに失敗する）。打ち、フォルダーを元に戻し、7 秒後に打ち、さらに 30 秒あまり待って打った。失敗しているあいだは、かなのまま入る（落ちない）。元に戻して 7 秒後は、まだかなのまま（やり直していない）。30 秒を過ぎたあとの最初の変換から、漢字に変換された。プロセスは同じまま（40-mozc-open-failed.png、41-mozc-recovered.png）。5 回でやめることは、単体テストでだけ確かめた。
性能のログの「種類」ログを有効にして、デバッグと release の両方で打った。キーの種類は kana、text、delete、space、enter、modify、switch と出る。release でも同じ名前で、書き換わった名前は出ない。
今までの動きが変わっていないことかなでの入力とライブ変換、候補のタップ、空白での候補送り、確定、削除（選択を解く、1 文字消す）、配列の切り替え（未確定文字がある状態で あ/A、記号、戻る、⇧）、数字の欄、ダーク（縦と横）。フリックの 55 通りと濁点の 165 通りも、このビルドで行った。仕様どおり。ダークでも読める（70-dark-portrait-selected.png）。
ログに打った文字が出ないこと修正のあとのビルドを入れた時点でログを消し、そこから確認が終わるまでのログをすべて取った（約 10 万 8 千行。release ビルドでの確認を含む）。自分のアプリのプロセス（13 個）が出した 8,858 行から、日本語の文字を探した。エミュレーター B でも同じことをした（105 行）。どちらも 0 行。日本語を含む行は、確認に使った道具（画面の構造を読むコマンド）のものだけ。異常終了と応答なしは 0 件。Mozc を開くのに失敗したときに出たのは、例外の種類の名前だけ。

修正のあとで分かった、気をつける点

  • 横画面で、アプリに残る高さは画面の半分に届かない（Android 15 で 46.6%、Android 8.0 で 45.6%）。直す前（31%）よりは広い。半分にするには、1 段を 37dp ほどまで下げる必要がある。仕様 04 の値（40dp と 36dp）のままにしてある。
  • 横画面にすると、Chrome のページ内の欄ではキーボードが閉じることがある（上の表）。
  • 横画面では、かなのキーが横に長い（幅 173dp、高さ 40dp）。フリックの判定はキーの幅の 1/4 なので、上下のフリックには約 43dp（キーの高さより長い距離）の移動が要る。adb で 150 ピクセル動かしたフリックは正しく入ったが、指での打ちやすさは実機で見る必要がある。直す前（54dp）も同じ判定だった。
  • URL の欄で確定キーを押すと、未確定文字があるときは確定だけが行われ、検索や移動はもう 1 回押したときに行われる（ほかの欄と同じ動き）。
  • キーボードのプロセスが落ちたあと、Chrome のページ内の欄ではキーボードが自分では出直さない（上の表）。修正の前からそうだったかは、確かめていない。
